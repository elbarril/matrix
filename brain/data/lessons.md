# lessons.md — the Zion Archive

Battle-tested lessons from real mistakes. These bind like the sacred foundation, but unlike it they are **amendable**: append a new lesson when reality teaches one. Read this at session start.

Routing: a lesson that binds across all projects lives here (the core pool). A lesson specific to one project lives in `brain/data/lessons/<project>.md` and loads only when the session binds to that project.

---

## Core lessons

1. **If it's not real, it doesn't matter.** No "done" without an end-to-end happy-path check. A passing unit test is not the same as the feature working. Smith + `validate_phase_close` gate the close. (Foundation 3.)

2. **Start simple, earn complexity.** The smallest thing that works ships first. Every added moving part must justify itself under a real constraint. The Architect's bias is fewer parts. (Foundation 4.)

3. **Load only what you need (The Construct).** Use `code-nav` for symbol-level reads/edits before opening whole files; delegate large artifacts (>~10 KB) to a sub-agent with a word cap; cheap model for mechanical work, reasoning model for hard problems. Context is the scarce resource.

4. **The brain never names a CLI.** Anything CLI-specific belongs in an adapter (the Trainman), never in `brain/`. If a lesson or workflow only works under one CLI, it's an adapter concern.

5. **State goes through the CLI.** Never hand-edit `.registry.json`, `brain/state/workspace.yaml`, `activity.log`, or `checkpoints.jsonl`. Use `bin/matrix`. Hand edits desync the ledger and the dashboard.

6. **Roster discipline.** Five core specialists. Adding one requires retiring or merging another. Proliferation (the old 9–12 roster) created overlap and maintenance cost with no gain.

7. **Checkpoint before truncating context.** On a long task or a mode change (build → eval → fix), write a checkpoint and a Link entry first. Resume is cheap; lost context is not.

8. **Never log secrets.** Not in checkpoints, agent output, commits, or the ledger. Scrub emails and tokens from anything that leaves the machine.

9. **Surface scope growth before doing it.** If a request quietly grows, stop and name it. Silent scope creep is a foundation violation, not helpfulness.

10. **Generated docs over hand-maintained docs.** The Source (`docs/SYSTEM_TRUTH.md`) is generated from the live brain and validated for drift. The old 22 hand-written docs drifted from reality; one generated doc cannot.

11. **No asumas gates de aprobación sin medirlos.** Se sospechó que un modo de ejecución no interactivo auto-deniega tools no aprobadas (basado en la documentación de un adapter concreto). 4 tests controlados (read-only y con side-effects, foreground vs. no-interactivo) no reprodujeron el bloqueo en este entorno. La causa real de un bloqueo pasado fue más probablemente el grant de capabilities del *perfil* del subagente, no el modo de ejecución. No construyas mitigación cara para un gap no reproducido — si vuelve a pasar, reabrilo con perfil/tool/versión concretos, no con la sospecha genérica. (Narrativa y citas específicas del adapter vigente — el flag exacto y el nombre de la doc citada — movidas a la documentación de ese adapter en la raíz del repo, sección «Lessons — detalle de adapter», lección 11.)

12. **Promové lessons vos mismo, no esperes a que te lo pidan dos veces.** Un hallazgo real y verificado (root cause confirmado, gap cerrado/reproducido, supuesto corregido) que solo queda en un checkpoint se pierde: el ledger scrollea fuera de la ventana que la activación repasa, `lessons.md` se lee completo siempre. Si la escritura es de bajo riesgo (append trivial a un lesson file, sin tocar state files a mano, sin costo de recursos relevante, sin downside serio si está mal — las lessons son amendable, no sacred foundation), promovela a `lessons.md` o al lesson de proyecto apenas la tengas, sin pedir aprobación. El usuario no debería tener que decir "che, guardá eso" — para eso está esta disciplina.

13. **Un tool-allowlist declarado en el artefacto del agente no restringe; una denylist de lectura a nivel de permisos del CLI sí, pero solo para el tool de lectura, no para `grep`/`exec`.** Evaluación real (Smith, 11 sesiones): el adapter vigente aplica una denylist de lectura sobre rutas incluso en su modo de permisos más abierto, y se propaga a subagentes. Esa misma denylist no bloquea `grep`/`glob` ni `exec` (`cat`, etc.), así que es una mitigación parcial contra lectura incidental, no un sandbox. Documentar siempre ese hueco en la salida del comando que toca esa denylist. (Mecánica exacta del adapter vigente — nombre del campo de config y del tool nativo — movida a su documentación en la raíz del repo, sección «Lessons — detalle de adapter», lección 13.)

14. **Medí la capacidad antes de diseñar alrededor de su ausencia.**
    1. **El sesgo va en las dos direcciones.** El sistema ya tenía la lección de no asumir que algo funciona sin verificarlo E2E. Falta su espejo: **no asumas que algo *no* funciona sin verificarlo tampoco.** Una limitación asumida es tan cara como una capacidad asumida — la segunda te rompe en runtime y te enterás; la primera te hace pagar complejidad para siempre y **nunca** te enterás.
    2. **La doc decía la verdad; nosotros no la creímos.** La documentación oficial de nesting de subagentes del adapter vigente documentaba el campo de profundidad desde el principio, y `capability-map.md` lo citaba correctamente ("subagents cannot spawn subagents **by default**") — la cláusula estaba ahí. El diseño leyó "by default" como "nunca". Corolario: cuando una doc dice *by default*, hay un override; buscalo antes de diseñar la vuelta larga. (Nombre exacto de la doc y del campo, movidos a la documentación del adapter vigente en la raíz del repo, sección «Lessons — detalle de adapter», lección 14.)
    3. **El costo del spike vs. el costo del rodeo.** El spike fue un subagente temporal con el campo de nesting-depth declarado y una llamada real de delegación/lectura de resultado. Minutos. El rodeo que evitó: un protocolo textual, un rol de courier en el master, un riesgo estructural, sus mitigaciones, un archivo de contrato, y una contradicción permanente entre el diagrama y el runtime. **Regla operable: si el diseño está por introducir un mecanismo cuya única justificación es "la plataforma no puede X", el spike de X es obligatorio antes de escribir el mecanismo.** (Nombres exactos de los tool calls usados en el spike, movidos a la documentación del adapter vigente, sección «Lessons — detalle de adapter», lección 14.)
    4. **Generalización a cualquier ship futuro:** la profundidad de nesting **no se declara a mano, se deriva** del grafo `captain`/`crew` del manifest — `depth_from_root + subtree_depth` — y la inyecta el Trainman en el artifact del capitán. Las hojas no llevan el campo. **Precondición honesta:** la fórmula está calibrada contra un único punto medido (`2`); un ship con sub-capitanes (profundidad ≥3) exige repetir el spike antes de confiar en ella.

15. **Una afirmación documental que no tiene código que la genere o gate que la valide se vuelve falsa con un refactor.** Generala desde el estado vivo o agregá una validación de drift.

16. **Con `set -euo pipefail`, capturar un comando que puede fallar requiere `|| rc=$?`.** Sin esa captura, el shell sale antes del camino de error; para gates de fase, eso convierte un BLOCK en evidencia no persistida.

17. **Una afirmación falsa rara vez vive solo en los dos archivos conocidos.** Antes de reconciliar texto, buscá la frase completa en el árbol y revisá cada resultado dentro del alcance.

18. **Una regla escrita en abstracto no se queda abstracta si el ejemplo que la ilustra es de una sola plataforma — y corregí la lección cuando la evidencia nueva la contradice, no la dejes como quedó escrita.** Primera pasada (Architect, agent_id=1b0251ef, feasibility review, sin medir) encontró 3 líos en `brain/agents/neo.md` y afirmó 2 supuestos sobre una plataforma alternativa que resultaron **falsos** al verificarlos contra su documentación oficial en la auditoría siguiente (agent_id=09c037aa, con lectura real de doc en vez de inferencia): esa plataforma alternativa SÍ anida subagentes por default, y SÍ expone identificadores de agente/tipo en el payload de sus hooks — ambos mejor que la plataforma vigente, no peor. El único hallazgo real que sobrevivió verificación: esa plataforma alternativa no tiene un primitivo de **resume de subagente** (el resume de sesión sí existe, pero no es direccionable a un hijo específico), así que el mecanismo de "resumir la sesión del mismo Trinity con el fix puntual" no porta; la forma portable es re-delegar a Trinity con un brief de fix. **Enmienda 2026-07-27:** la parte de esta lección que decía "la doctrina sobrevive (Smith nunca aplica su propio fix)" **ya no es cierta** — por decisión del usuario, Smith pasó a evaluador-con-remediación y arregla él mismo los defectos Tier 1/Tier 2 que reportó (diseño y compensadores en `brain/output/architecture/matrix-smith-evaluator-with-remediation-adr.md`; texto exacto aplicado en `brain/agents/smith.md` y `brain/agents/neo.md`, con backstop mecánico en `hooks/post_run_audit.py`). Lo que la enmienda **confirma** es justamente la regla operable de esta lección: la propiedad "barato, reusa contexto" era una ventaja de una sola plataforma y no debió sostener una doctrina de coordinación; al quitarla, el handoff que justificaba desapareció. Regla operable, sin cambios: cuando una doctrina de coordinación depende de una capacidad de plataforma no verificada, marcarla "requiere verificación por adapter" al escribirla — y cuando la doctrina cambia, enmendar la lección citando el cambio real (archivo + fecha), nunca dejarla afirmando el estado viejo (lección 20). (Nombres exactos de las dos plataformas citadas, movidos a la documentación del adapter vigente en la raíz del repo, sección «Lessons — detalle de adapter», lección 18.)

19. **Gatear una defensa fail-loud con permisos restringidos da un falso PASS.** Al probar R6 (Niobe debe abortar si no puede spawnear tripulación, nunca auto-graduarse) con permisos por defecto, una denegación de escritura/exec habría producido el mismo síntoma externo ("no hizo nada") que un abort real — indistinguibles desde afuera. La prueba solo es válida corriendo con un modo de permisos sin restricciones (adapter-specific flag) y `write`/`edit`/`exec` disponibles, así la única cosa que puede frenar al agente es su propia disciplina declarada, no una denegación externa. Regla general: para gatear cualquier defensa de "el agente elige no hacer X", remové primero las barreras externas que también le impedirían X — si no podés distinguir "no quiso" de "no pudo", el gate no probó nada. (Nombre exacto del flag de permisos del adapter vigente movido a su documentación en la raíz del repo, sección «Lessons — detalle de adapter», lección 19.)

20. **Una lección sobre supuestos de plataforma no verificados tiene que citar una medición, no una revisión de documento.** La lección 18 original nació de una feasibility review (lectura + inferencia, sin spike) y afirmó 2 de 3 supuestos sobre una plataforma alternativa que resultaron falsos al re-verificarlos con lectura real de su documentación en la auditoría siguiente — la lección 14 recurrió adentro de la lección escrita para prevenirla. Regla operable: cuando una lección hace una afirmación sobre "lo que otra plataforma puede o no puede hacer", exigí que cite la línea/doc exacto verificado (no "según el análisis previo" ni "se documentó que"), y si nadie lo verificó todavía, escribila como pregunta abierta, no como hallazgo. (Nombre exacto de la plataforma alternativa citada, movido a la documentación del adapter vigente en la raíz del repo, sección «Lessons — detalle de adapter», lección 20.)

21. **Un claim de arquitectura ("cambiás un adapter chico y nada más") es una afirmación falsificable, no una aspiración — auditala como tal.** Auditoría repo-wide (Architect, agent_id=09c037aa, 2026-07-27) encontró 29 puntos de acoplamiento al adapter vigente fuera de su propio directorio (16 en `brain/`, 6 en `hooks/`+`bin/matrix`, 7 en `_build.py`/docs), de los cuales 3 producen **falso verde**: `hooks/validate_ship.py` reporta PASS si no encuentra los artifacts de ese adapter en vez de fallar fuerte; `bin/matrix`'s `path_is_bound()` define "bound" por la presencia de un archivo de formato específico de ese adapter como parte del predicado de estado; `adapters/_harden.py` adivina una ruta de config para cualquier target desconocido y reporta éxito al escribir un archivo que esa plataforma nunca lee. Regla operable: cuando falta soporte para un target nuevo, la falla correcta es ruidosa ("no implementado para X"), nunca un PASS silencioso por ausencia de evidencia — un hook que no puede validar algo tiene que decir "no puedo validar esto", no "está bien". (Nombre exacto del adapter vigente citado en el hallazgo original, movido a su documentación en la raíz del repo, sección «Lessons — detalle de adapter», lección 21.)

22. **Un hallazgo grande de un subagente se persiste completo en `brain/output/` (o `matrix-output/` con proyecto bindeado) en el momento, no se resume solo en un checkpoint.** La auditoría de acoplamiento CLI de agent_id=09c037aa (lección 21) nunca se guardó como archivo — sobrevivió solo como resumen de checkpoint y como la versión condensada de la lección 21 misma. Una sesión de Smith que fue a re-verificarla tuvo que reconstruir el detalle desde cero porque `brain/output/architecture/` solo tenía un `.gitkeep`. `architect.md:33` ya declara `matrix-output/architecture/<project>-<surface>.md` como el path correcto para exactamente este tipo de artefacto. Regla operable: el checkpoint es un puntero al artefacto, nunca un sustituto — si un subagente devuelve un hallazgo de investigación/diseño de más de unas pocas líneas, escribilo a disco en el mismo turno en que lo recibís, antes de seguir a la próxima tarea.

23. **La misma sesión que escribe la lección sobre un problema puede seguir cometiéndolo — corregir en prosa no es corregir en la práctica.** Re-verificación en vivo (Smith, agent_id=f920c882, 2026-07-27) de los 29 hallazgos de la lección 21 encontró: 27 siguen presentes, 0 arreglados, y varios archivos de doctrina **crecieron** en acoplamiento a un CLI concreto durante la misma ventana de trabajo que documentó el problema (incluidas las propias lecciones 18/20/21, que nombraban plataformas concretas en `brain/`). La causa raíz medida (no inferida): la regla "el brain nunca nombra un CLI" tenía **cero enforcement mecánico** en todo el repo — ni hook, ni lint, ni CI — pese a que el patrón exacto necesario ya existía (`hooks/validate_ship.py:66-89`, un content-lint para una regla distinta) y nunca se apuntó a `brain/`. Regla operable: una regla "de oro" sin gate que la mida es una aspiración, no una regla — si se repite una violación después de documentarla en prosa dos veces, el siguiente paso obligatorio es un chequeo mecánico, no una tercera prosa. (Nombres exactos de los archivos y su conteo de menciones por CLI, movidos a la documentación del adapter vigente en la raíz del repo, sección «Lessons — detalle de adapter», lección 23.)

(Nombre exacto del flag de permisos del adapter vigente movido a su documentación en la raíz del repo, sección «Lessons — detalle de adapter», lección 24; ver también lección 19, hallazgo gemelo.)

25. **Una fixture inyectada a mano puede validar el criterio y ocultar el bug del productor real.** P7 (session-scoping de `phase close`): el criterio "sesión que cierra bien pasa el gate" se probó escribiendo a mano un evento de audit log con un `session_id` correcto — pasó. El bug real era que el productor (`bin/matrix phase_close()`) nunca escribía ese `session_id` correcto (correlacionaba con un marker de sesión stale, porque una restricción de diseño sobre cómo el CLI vigente expone el session id a los hooks quedó obsoleta con una versión nueva del CLI y nadie la re-midió). La fixture simuló el resultado, no el productor, y el gate dio un falso verde. Regla: la fixture puede simular el *escenario* (orden de eventos, timing), pero el dato que el bug realmente rompe tiene que salir del *productor real* corriendo, no de un valor tipeado a mano — si no, probaste el consumidor contra tu propia expectativa, no contra el sistema. (Nombre exacto del CLI y de la restricción de diseño original citada, movidos a la documentación del adapter vigente en la raíz del repo, sección «Lessons — detalle de adapter», lección 25.)

26. **Un `diff` byte-idéntico entre lo generado y lo instalado prueba lo que se escribió en disco, no lo que un subagente ya en curso puede usar.** Al re-otorgarle `edit` a Smith (rol de evaluador-con-remediación, 2026-07-27), Trinity verificó que el artifact generado y el instalado eran idénticos y lo dio por medido. El spike en vivo posterior, en el mismo proceso de CLI que corrió la instalación, mostró que una sesión de Smith recién spawneada solo tenía un subconjunto de tools (sin edición/creación de archivo) pese a que el archivo en disco ya los declaraba. Ninguna doc revisada especifica si la resolución de tools de un subagente se cachea al arrancar el proceso de CLI o se lee en vivo; quedó como pregunta abierta, no como hallazgo (regla de la lección 20), con la hipótesis más simple (snapshot al inicio del proceso) sin confirmar. Regla operable: un chequeo de archivo (`diff`, lectura de frontmatter) prueba que el *Trainman* escribió bien; solo un spike de subagente real, en un proceso de CLI iniciado *después* del cambio, prueba que la plataforma ya lo sirve — no asumas que ambos momentos coinciden. (Nombres exactos de los tool calls y de las docs consultadas, movidos a la documentación del adapter vigente en la raíz del repo, sección «Lessons — detalle de adapter», lección 26.)

27. **Una etiqueta de capacidad no prueba cada tool individual, y un audit log de subagente no prueba atribución individual.** El spike de Neo en un proceso de CLI genuinamente nuevo confirmó la hipótesis pendiente de la lección 26: el subagente evaluador recién spawneado reportó edición de archivo existente viva, mientras que un perfil sin esa capacidad declarada siguió sin tenerla. La resolución del tool-allowlist queda confirmada como snapshot al inicio del proceso de CLI. Al mismo tiempo, ese mismo self-report mostró la creación de archivo ausente pese a estar declarada en el tool-allowlist instalado, así que la capacidad abstracta `edit` mapeada a [editar, crear] no garantiza que ambos se expongan en vivo; solo la edición de archivos existentes está confirmada, la creación de archivos no. Por último, una llamada de edición real del subagente evaluador llegó al audit log local con el nombre de tool y las rutas correctas, pero el identificador de sesión registrado fue el de la sesión padre, no un id propio del subagente; el audit log de hoy no puede distinguir una llamada directa del master de una llamada de su subagente. Regla operable: después de cambiar un tool-allowlist, medí cada tool por su nombre en un proceso de CLI nuevo, y no asumas que el audit log identifica quién originó la llamada hasta que la plataforma asigne un identificador de sesión distinto a cada subagente. Un segundo spike independiente en un proceso fresco confirmó que la creación de archivo y las tools de un servidor MCP de navegador están **CONFIRMED ABSENT** para subagentes independientemente de su declaración en el tool-allowlist: no era un problema de timing/snapshot — el mismo patrón de proceso fresco que hizo aparecer la edición no hizo aparecer la creación ni ninguna tool MCP — mientras que la búsqueda de archivos por nombre sí está presente bajo otro nombre nativo. Addendum operable: algunos mappings capacidad→tool que funcionan para el agente root/foreground no se propagan en absoluto a subagentes en esta plataforma, independientemente del timing del proceso; tratá la creación de archivo y cualquier tool de servidor MCP como no confirmada hasta medirla para cada perfil de subagente que la declare, no solo el evaluador. Un caso medido después mostró que una sesión del evaluador sí logró crear un artefacto nuevo pese a la creación estar ausente y la edición rechazar rutas inexistentes (confirmado por un intento directo que falló igual); el único mecanismo consistente con las capacidades es ejecución de comando con redirección de shell, no re-verificado como la llamada literal en esa sesión (una inferencia, no una traza de tool observada) pero la única explicación consistente dado el comportamiento confirmado de las otras dos tools. (Nombres exactos de los tool calls nativos, de los perfiles de subagente y del servidor MCP citados, movidos a la documentación del adapter vigente en la raíz del repo, sección «Lessons — detalle de adapter», lección 27.)
