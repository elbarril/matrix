# lessons.md — the Zion Archive

Battle-tested lessons from real mistakes. These bind like the sacred foundation, but unlike it they are **amendable**: append a new lesson when reality teaches one. Read this at session start.

Routing: a lesson that binds across all projects lives here (the core pool). A lesson specific to one project lives in `brain/data/lessons/<project>.md` and loads only when the session binds to that project.

---

## Core lessons

1. **If it's not real, it doesn't matter.** No "done" without an end-to-end happy-path check. A passing unit test is not the same as the feature working. Smith + `validate_phase_close` gate the close. (Foundation 3.)

2. **Start simple, earn complexity.** The smallest thing that works ships first. Every added moving part must justify itself under a real constraint. The Architect's bias is fewer parts. (Foundation 4.)

3. **Load only what you need (The Construct).** Use `code-nav` for symbol-level reads/edits before opening whole files; delegate large artifacts (>~10 KB) to a sub-agent with a word cap; cheap model for mechanical work, reasoning model for hard problems. Context is the scarce resource.

4. **The brain never names a CLI.** Anything CLI-specific belongs in an adapter (the Trainman), never in `brain/`. If a lesson or workflow only works under one CLI, it's an adapter concern.

5. **State goes through the CLI.** Never hand-edit `.registry.json`, `brain/state/workspace.yaml`, `activity.log`, or `checkpoints.jsonl`. Use `bin/matrix`. Hand edits desync the ledger and the dashboard.

6. **Roster discipline.** Five core specialists. Adding one requires retiring or merging another. Proliferation (the old 9–12 roster) created overlap and maintenance cost with no gain.

7. **Checkpoint before truncating context.** On a long task or a mode change (build → eval → fix), write a checkpoint and a Link entry first. Resume is cheap; lost context is not.

8. **Never log secrets.** Not in checkpoints, agent output, commits, or the ledger. Scrub emails and tokens from anything that leaves the machine.

9. **Surface scope growth before doing it.** If a request quietly grows, stop and name it. Silent scope creep is a foundation violation, not helpfulness.

10. **Generated docs over hand-maintained docs.** The Source (`docs/SYSTEM_TRUTH.md`) is generated from the live brain and validated for drift. The old 22 hand-written docs drifted from reality; one generated doc cannot.

11. **No asumas gates de aprobación sin medirlos.** Se sospechó que subagents en background auto-deniegan tools MCP no aprobadas (basado en `subagents.mdx`). 4 tests controlados (MCP read-only y con side-effects, foreground vs background) no reprodujeron el bloqueo en este entorno. La causa real de un bloqueo pasado (figma-audit) fue más probablemente el grant de capabilities del *perfil* del subagente, no el flag `is_background`. No construyas mitigación cara para un gap no reproducido — si vuelve a pasar, reabrilo con perfil/tool/versión concretos, no con la sospecha genérica.

12. **Promové lessons vos mismo, no esperes a que te lo pidan dos veces.** Un hallazgo real y verificado (root cause confirmado, gap cerrado/reproducido, supuesto corregido) que solo queda en un checkpoint se pierde: el ledger scrollea fuera de la ventana que la activación repasa, `lessons.md` se lee completo siempre. Si la escritura es de bajo riesgo (append trivial a un lesson file, sin tocar state files a mano, sin costo de recursos relevante, sin downside serio si está mal — las lessons son amendable, no sacred foundation), promovela a `lessons.md` o al lesson de proyecto apenas la tengas, sin pedir aprobación. El usuario no debería tener que decir "che, guardá eso" — para eso está esta disciplina.

13. **`allowed-tools` en SKILL.md no restringe; `permissions.deny` con `Read()` sí, pero solo para el tool `read`, no `grep`/`exec`.** Evaluación real (Smith, 11 sesiones): Devin aplica `deny: ["Read(<ruta>/**)"]` sobre `read_file` inclusive en `--permission-mode dangerous`, y se propaga a subagentes. Ese mismo `deny` no bloquea `grep`/`glob` ni `exec` (`cat`, etc.), así que es una mitigación parcial contra lectura incidental, no un sandbox. Documentar siempre ese hueco en la salida del comando que toca `permissions.deny`.

14. **Medí la capacidad antes de diseñar alrededor de su ausencia.**
    1. **El sesgo va en las dos direcciones.** El sistema ya tenía la lección de no asumir que algo funciona sin verificarlo E2E. Falta su espejo: **no asumas que algo *no* funciona sin verificarlo tampoco.** Una limitación asumida es tan cara como una capacidad asumida — la segunda te rompe en runtime y te enterás; la primera te hace pagar complejidad para siempre y **nunca** te enterás.
    2. **La doc decía la verdad; nosotros no la creímos.** `subagents.mdx` "Nesting Depth" documentaba `max-nesting` desde el principio, y `capability-map.md` lo citaba correctamente ("subagents cannot spawn subagents **by default**") — la cláusula estaba ahí. El diseño leyó "by default" como "nunca". Corolario: cuando una doc dice *by default*, hay un override; buscalo antes de diseñar la vuelta larga.
    3. **El costo del spike vs. el costo del rodeo.** El spike fue un subagente temporal, un `max-nesting: 2`, un `run_subagent`, un `read_subagent`. Minutos. El rodeo que evitó: un protocolo textual, un rol de courier en el master, un riesgo estructural, sus mitigaciones, un archivo de contrato, y una contradicción permanente entre el diagrama y el runtime. **Regla operable: si el diseño está por introducir un mecanismo cuya única justificación es "la plataforma no puede X", el spike de X es obligatorio antes de escribir el mecanismo.**
    4. **Generalización a cualquier ship futuro:** la profundidad de nesting **no se declara a mano, se deriva** del grafo `captain`/`crew` del manifest — `depth_from_root + subtree_depth` — y la inyecta el Trainman en el artifact del capitán. Las hojas no llevan el campo. **Precondición honesta:** la fórmula está calibrada contra un único punto medido (`2`); un ship con sub-capitanes (profundidad ≥3) exige repetir el spike antes de confiar en ella.

15. **Una afirmación documental que no tiene código que la genere o gate que la valide se vuelve falsa con un refactor.** Generala desde el estado vivo o agregá una validación de drift.

16. **Con `set -euo pipefail`, capturar un comando que puede fallar requiere `|| rc=$?`.** Sin esa captura, el shell sale antes del camino de error; para gates de fase, eso convierte un BLOCK en evidencia no persistida.

17. **Una afirmación falsa rara vez vive solo en los dos archivos conocidos.** Antes de reconciliar texto, buscá la frase completa en el árbol y revisá cada resultado dentro del alcance.

18. **Una regla escrita en abstracto no se queda abstracta si el ejemplo que la ilustra es de una sola plataforma — y corregí la lección cuando la evidencia nueva la contradice, no la dejes como quedó escrita.** Primera pasada (Architect, agent_id=1b0251ef, feasibility review, sin medir) encontró 3 líos en `brain/agents/neo.md` y afirmó 2 supuestos sobre Claude Code que resultaron **falsos** al verificarlos contra `claude-master-documentation/docs/` en la auditoría siguiente (agent_id=09c037aa, con lectura real de doc en vez de inferencia): Claude Code SÍ anida subagentes por default (profundidad 3, sin opt-in) y SÍ expone `agent_id`/`agent_type` en el payload de sus hooks — ambos mejor que Devin, no peor. El único hallazgo real que sobrevivió verificación: Claude Code no tiene un primitivo de **resume de subagente** (el resume de sesión sí existe, pero no es direccionable a un hijo específico), así que el patrón *Secure build* de `neo.md:57,98` (resumir la sesión del mismo Trinity con el fix puntual) no porta — la doctrina sobrevive (Smith nunca aplica su propio fix) pero se pierde la propiedad de "barato, reusa contexto"; portarlo real es re-delegar a Trinity con un brief de fix. Regla operable, sin cambios: cuando una doctrina de coordinación depende de una capacidad de plataforma no verificada, marcarla "requiere verificación por adapter" al escribirla — pero además, la corrección meta (ver lección 20) es la parte nueva de esta entrada.

19. **Gatear una defensa fail-loud con permisos restringidos da un falso PASS.** Al probar R6 (Niobe debe abortar si no puede spawnear tripulación, nunca auto-graduarse) con permisos por defecto, una denegación de escritura/exec habría producido el mismo síntoma externo ("no hizo nada") que un abort real — indistinguibles desde afuera. La prueba solo es válida corriendo con permisos abiertos (`--permission-mode dangerous` o equivalente) y `write`/`edit`/`exec` disponibles, así la única cosa que puede frenar al agente es su propia disciplina declarada, no una denegación externa. Regla general: para gatear cualquier defensa de "el agente elige no hacer X", remové primero las barreras externas que también le impedirían X — si no podés distinguir "no quiso" de "no pudo", el gate no probó nada.

20. **Una lección sobre supuestos de plataforma no verificados tiene que citar una medición, no una revisión de documento.** La lección 18 original nació de una feasibility review (lectura + inferencia, sin spike) y afirmó 2 de 3 supuestos sobre Claude Code que resultaron falsos al re-verificarlos con lectura real de `docs/` en la auditoría siguiente — la lección 14 recurrió adentro de la lección escrita para prevenirla. Regla operable: cuando una lección hace una afirmación sobre "lo que otra plataforma puede o no puede hacer", exigí que cite la línea/doc exacto verificado (no "según el análisis previo" ni "se documentó que"), y si nadie lo verificó todavía, escribila como pregunta abierta, no como hallazgo.

21. **Un claim de arquitectura ("cambiás un adapter chico y nada más") es una afirmación falsificable, no una aspiración — auditala como tal.** Auditoría repo-wide (Architect, agent_id=09c037aa, 2026-07-27) encontró 29 puntos de acoplamiento a Devin fuera de `adapters/devin/` (16 en `brain/`, 6 en `hooks/`+`bin/matrix`, 7 en `_build.py`/docs), de los cuales 3 producen **falso verde**: `hooks/validate_ship.py` reporta PASS si no encuentra artifacts de Devin en vez de fallar fuerte; `bin/matrix`'s `path_is_bound()` define "bound" por la presencia de `AGENTS.local.md` (formato Devin) como parte del predicado de estado; `adapters/_harden.py` adivina una ruta de config para cualquier target desconocido y reporta éxito al escribir un archivo que esa plataforma nunca lee. Regla operable: cuando falta soporte para un target nuevo, la falla correcta es ruidosa ("no implementado para X"), nunca un PASS silencioso por ausencia de evidencia — un hook que no puede validar algo tiene que decir "no puedo validar esto", no "está bien".

22. **Un hallazgo grande de un subagente se persiste completo en `brain/output/` (o `matrix-output/` con proyecto bindeado) en el momento, no se resume solo en un checkpoint.** La auditoría de acoplamiento CLI de agent_id=09c037aa (lección 21) nunca se guardó como archivo — sobrevivió solo como resumen de checkpoint y como la versión condensada de la lección 21 misma. Una sesión de Smith que fue a re-verificarla tuvo que reconstruir el detalle desde cero porque `brain/output/architecture/` solo tenía un `.gitkeep`. `architect.md:33` ya declara `matrix-output/architecture/<project>-<surface>.md` como el path correcto para exactamente este tipo de artefacto. Regla operable: el checkpoint es un puntero al artefacto, nunca un sustituto — si un subagente devuelve un hallazgo de investigación/diseño de más de unas pocas líneas, escribilo a disco en el mismo turno en que lo recibís, antes de seguir a la próxima tarea.

23. **La misma sesión que escribe la lección sobre un problema puede seguir cometiéndolo — corregir en prosa no es corregir en la práctica.** Re-verificación en vivo (Smith, agent_id=f920c882, 2026-07-27) de los 29 hallazgos de la lección 21 encontró: 27 siguen presentes, 0 arreglados, y `niobe.md` (0→4 menciones), `capability-map.md` (8→10) y `lessons.md` (+4, las propias lecciones 18/20/21 nombran Devin/Claude Code en `brain/`) **crecieron** en acoplamiento durante la misma ventana de trabajo que documentó el problema. La causa raíz medida (no inferida): la regla "el brain nunca nombra un CLI" tiene **cero enforcement mecánico** en todo el repo — ni hook, ni lint, ni CI — pese a que el patrón exacto necesario ya existe (`hooks/validate_ship.py:66-89`, un content-lint para una regla distinta) y nunca se apuntó a `brain/`. Regla operable: una regla "de oro" sin gate que la mida es una aspiración, no una regla — si se repite una violación después de documentarla en prosa dos veces, el siguiente paso obligatorio es un chequeo mecánico, no una tercera prosa.

24. **Gatear una defensa fail-loud con permisos restringidos da un falso PASS.** Al probar R6 de Logos (Niobe debe abortar si no puede spawnear tripulación, nunca auto-graduarse) con permisos por defecto, una denegación de escritura/exec habría producido el mismo síntoma externo ("no hizo nada") que un abort real — indistinguibles desde afuera. La prueba solo es válida corriendo con permisos abiertos (`--permission-mode dangerous` o equivalente) y `write`/`edit`/`exec` disponibles, así la única cosa que puede frenar al agente es su propia disciplina declarada, no una denegación externa. Regla general: para gatear cualquier defensa de "el agente elige no hacer X", remové primero las barreras externas que también le impedirían X — si no podés distinguir "no quiso" de "no pudo", el gate no probó nada.

25. **Una fixture inyectada a mano puede validar el criterio y ocultar el bug del productor real.** P7 (session-scoping de `phase close`): el criterio "sesión que cierra bien pasa el gate" se probó escribiendo a mano `{"event":"phase_close","session_id":"<sid correcto>"}` en el audit log — pasó. El bug real era que el productor (`bin/matrix phase_close()`) nunca escribía ese `session_id` correcto (correlacionaba con un marker de sesión stale, porque la restricción de diseño "Devin no expone session id a los hooks" quedó obsoleta con una versión nueva del CLI y nadie la re-midió). La fixture simuló el resultado, no el productor, y el gate dio un falso verde. Regla: la fixture puede simular el *escenario* (orden de eventos, timing), pero el dato que el bug realmente rompe tiene que salir del *productor real* corriendo, no de un valor tipeado a mano — si no, probaste el consumidor contra tu propia expectativa, no contra el sistema.
