# FEDERATION.md — Federated ships (the fleet)

A **ship** is a subsystem with its own captain, crew, contract, and `AGENTS.md` under `brain/subsystems/<ship>/`. Ships coordinate with the core and with each other only through the shared **Link** ledger — they never reach into another ship's state or into `brain/state/`.

The canonical example is the **Logos** deep-research ship (captain Niobe, crew Ghost + Sparks). The core vessel is the **Nebuchadnezzar**.

## 1. What a ship is

- Owns a capability discipline that would bloat the core roster (e.g., deep research with evidence grading).
- Has a single captain who is the only voice of the ship toward the core.
- Keeps its own `AGENTS.md` with a YAML frontmatter manifest.
- Is lazy-loaded: Neo routes to the captain only when the `route-when` trigger fires.

## 2. The manifest schema

Each `brain/subsystems/<ship>/AGENTS.md` begins with a frontmatter block:

```yaml
---
ship: <ship-slug>
captain: <captain-agent>
crew: [<agent1>, <agent2>, ...]
crew-max: <N>
route-when: <prose trigger criteria>
writes: [<event:namespace>]
reads: [<event:namespace>]
state: <relative-path-to-ship-state>
request: <event:namespace>
result: <event:namespace>
---
```

| Field | Meaning |
|---|---|
| `ship` | Ship slug (matches directory name). |
| `captain` | The ship's master; the only agent the core talks to. |
| `crew` | List of internal crew members; the captain may spawn them directly. |
| `crew-max` | Hard roster limit for this ship (3 for Logos). |
| `route-when` | Prosa criteria that Neo uses to decide when to route here. |
| `writes` | Event namespaces the ship writes to the ledger. |
| `reads` | Event namespaces the ship reads from the ledger. |
| `state` | Ship-local state path (must be gitignored). |
| `request` / `result` | Events the core and ship use to hand off work. |

## 3. Integration checklist

Run `bin/matrix hooks validate_ship '{"ship":"*"}'` to verify every ship. The hook is the source of truth for this checklist.

| # | Item | Verified by |
|---|---|---|
| 1 | Manifest parses and has all required keys | `validate_ship` check `manifest_parses` |
| 2 | Captain file exists and is a valid agent | `validate_ship` check `captain_present` |
| 3 | Crew files exist and are valid agents | `validate_ship` check `crew_present` |
| 4 | `len(crew) + 1 ≤ crew-max` | `validate_ship` check `roster_discipline` |
| 5 | Ship state is not under `brain/state/` and ship files do not mention it | `validate_ship` check `no_core_state` (heuristic) |
| 6 | Ship state path is gitignored | `validate_ship` check `state_gitignored` |
| 7 | Corpus has one appraisal per source and no self-grading | `validate_ship` check `corpus_shape` (when data exists) |
| 8 | Captain artifact carries the correct `max-nesting` value; leaves do not | `validate_ship` check `max_nesting` |

The `<ship>-<agent>` prefix, generated by `adapters/_build.py`, is the structural defense against name collisions. There is no `no_name_collision` check: it was removed from the design as redundant. Reopen the analysis if ship slugs with hyphens are admitted.

## 4. Coordination protocol

The core and a ship communicate through the Link ledger:

1. **Neo** writes `research:request <slug> --ref=<R>`.
2. **Neo** spawns the ship's captain once with the request.
3. **Captain** immediately before each dispatch logs `bin/matrix link crew:task <ship-slug> --ref=<R> "profile=<ship>-<agent> crew=<agent> topic=<topic> <free text>"`; the subject is only the ship slug, and `profile=`, `crew=`, `topic=`, and free text are detail. It then dispatches with `run_subagent` and reads the crew back via `read_subagent`. `profile=` is the captain's declaration of intent before dispatch, not a runtime measurement: it does not prove what Devin actually spawned (that is in `sessions.db`, outside the ledger's scope).
4. **Captain** runs the integrity gate and writes `research:result <slug> --ref=<R>`.
5. **Neo** reads the result and presents it to the user.

`bin/matrix activity` filters by the resolved project by default. Ship events (whose subject is the ship slug) therefore do not appear in the default view; use `--all` or `--project=<ship>` to see them.

Neo never knows the crew members of a ship. The captain is the only surface.

## 5. Spawn-direct pattern (canonical)

Under Devin, a ship captain is generated with a `max-nesting` frontmatter field that authorizes it to spawn its crew. This removes the need for courier protocols like the old `CREW-ORDER`. Requirements:

- The captain declares `run-subagent` in its brain capabilities.
- The Trainman injects `max-nesting: <N>` into the captain's generated artifact only.
- Crew leaves do **not** carry `max-nesting`; they cannot spawn anything.
- If the captain cannot spawn a crew member, it aborts with `LOGOS_ABORTED: crew unreachable` and reports — never falls back to self-grading or self-ingesting.

## 6. Nesting depth

The required `max-nesting` value is derived from the ship manifest graph:

```text
required_nesting(agent) = depth_from_root(agent) + subtree_depth(agent)
```

- **Logos** (flat): Niobe is depth 1 from Neo, her crew is depth 2. Niobe's `subtree_depth` is 1 (direct leaves), so `max-nesting = 2`. Ghost and Sparks have no children, so they get no field.
- The formula is **verified only for depth 2**. A ship with sub-captains (depth ≥3) requires a new nesting spike before the formula can be trusted.

## 7. Procedure: add a ship

1. Create `brain/subsystems/<ship>/AGENTS.md` with the manifest frontmatter.
2. Create `brain/subsystems/<ship>/agents/<captain>.md` and crew agents.
3. Define ship-local state (e.g., `corpus/`) and ensure `.gitignore` covers it.
4. Run `bin/matrix hooks validate_ship '{"ship":"<ship>"}'`.
5. Run `bin/matrix build --target=devin && bin/matrix install --target=devin`.
6. Re-run `validate_ship` and `the_source --check`.
