Matrix

Personal Intelligence Engine — construido para Devin CLI

Un cerebro que vive en un repo y se conecta a tus proyectos por symlink. Esta escrito para ser CLI-agnostico (habla en capacidades, nunca en herramientas de un CLI puntual), pero hoy el unico adaptador implementado y mantenido es Devin.

1. Que es Matrix

Matrix es tu capa de inteligencia personal. Un repositorio raiz (matrix/) contiene el cerebro. Tus proyectos viven afuera, se traen on-demand, y se conectan al cerebro via un symlink _brain. La inteligencia nunca se copia al proyecto.

La tesis central: los agentes, las lecciones y el contrato se escriben una sola vez en markdown, hablando de capacidades abstractas (read, edit, search, code-nav...), nunca de un CLI puntual. Un adaptador fino («The Trainman») traduce esas capacidades a las herramientas nativas del CLI que estes usando.

2. Las tres capas


LAYER 3 — Adapters · "The Trainman"
  adapters/devin/   (adapters/<otro>/ mas adelante, ninguno mas existe hoy)
  Transito entre mundos. Mapea capacidades a herramientas nativas.
  Genera artefactos: bin/matrix build --target=devin
  Los despliega globalmente: bin/matrix install --target=devin

LAYER 2 — Intelligence core · "Zion" (agnostic markdown)
  brain/agents/      → Neo (master) + especialistas
  brain/data/        → lessons, capability-map, code-quality lens
  AGENTS.md          → el contrato canonico
  NUNCA nombra un CLI. Habla en capacidades.

LAYER 1 — Orquestacion & infraestructura
  bin/matrix   → registry, proyectos, checkpoints, ledger (Link)
  hooks/       → enforcement portable (Seraph)
  brain/state/ → estado file-based
  No sabe nada de agentes. Gestiona estado y dispara hooks.

Regla de oro: la Capa 2 nunca nombra un CLI. Si algo solo funciona bajo un CLI, pertenece a un adaptador (Capa 3), no al cerebro.

3. El roster (agentes)

Un master, cinco especialistas core, un sexto opt-in. Disciplina de roster: agregar uno requiere retirar o fusionar otro.

MASTER Neo

The One. La unica voz. Rutea, sostiene contexto, lleva la sacred foundation. El usuario siempre habla con Neo primero.

RESEARCH The Oracle

Investiga, compara, cita, preve. Responde «que existe / que es verdad». Nunca afirma sin fuente.

PLAN Morpheus

Convierte ambiguedad en scope ordenado. Responde «que / cuando». «Solo puedo mostrarte la puerta.»

ARCHITECT The Architect

Disena estructura, nombra trade-offs, revisa el plan antes de construir. Responde «como encaja».

BUILD Trinity

Implementa y entrega. Codigo real que corre. Sigue el diseno del Architect; no improvisa estructura.

EVAL Agent Smith

Testea, critica, bloquea trabajo debil. Root-cause de bugs. Dueno del reality gate: nada esta «listo» sin un check E2E. Para trabajo visual, usa la capacidad browser (screenshot real, no descripcion). Desde el cambio de rol, tambien arregla las fallas de bajo riesgo que el mismo reporto: primero congela el comando que falla y su salida cruda, despues aplica el fix minimo, despues vuelve a correr el mismo comando. Lo estructural (estado del sistema, logica de gates, el contrato) sigue yendo a Trinity.

OPT-IN The Keymaker

Git / Ops. Ramas, commits, merge, acceso. Solo se activa cuando el trabajo git es explicito. Nunca autonomo.

6. Quick Start

# 1. Registrar un proyecto
./bin/matrix add mi-proyecto /ruta/al/proyecto

# 2. Seleccionarlo (crea el symlink _brain)
./bin/matrix select mi-proyecto

# 3. Verificar
./bin/matrix status

# 4. (Opcional) Calentar multiples proyectos
./bin/matrix work mi-proyecto
./bin/matrix work otro-proyecto
./bin/matrix bindings --warm-only

# 5. Generar artefactos nativos y desplegarlos globalmente (Devin)
./bin/matrix build   --target=devin
./bin/matrix install --target=devin

# 6. Invocar a Neo desde Devin CLI, en cualquier proyecto
#    /neo

# 7. Escribir un checkpoint cuando algo importa
./bin/matrix checkpoint "Completado el fix del login"

# 8. Ver el ledger de actividad
./bin/matrix activity 10

7. Enforcement (Seraph)

Hooks portables en hooks/, Python/bash con contrato JSON in/out. Se corren via bin/matrix hooks <nombre>.

Tabla de hooks (11 hooks)
HookQue haceCuando
pre_activation_check Valida: contrato presente, config valida, roster intacto, estado OK Antes de que cualquier agente actue
validate_phase_close Bloquea cerrar una fase sin evidencia real E2E. Implementa Foundation 3. En phase=eval tambien exige un campo lesson no trivial (que se capturo y donde, o un N/A razonado) — no escribe nada en disco, solo devuelve PASS/BLOCK Antes de declarar una fase «done»
post_run_audit Verifica que los pasos enforced corrieron (proceso, no contenido), detecta bypass, escribe validation-report.json Despues de una corrida
the_source Genera docs/SYSTEM_TRUTH.md desde el brain vivo. Con {"check":true} valida que no hay drift. Mantenimiento / verificacion
audit_event Log append-only de metadatos de eventos de ciclo de vida (metadata-only, nunca contenido de prompts) Cada evento de lifecycle
session_close Cierre manual/CI de sesion: reconstruye los pasos desde el audit log y corre post_run_audit para generar el reporte de validacion Al cerrar una sesion

Dos gates, dos preguntas distintas: validate_phase_close audita el contenido (¿el trabajo es real?) y no persiste nada — es el agente quien decide invocarlo al cerrar una fase. post_run_audit audita el proceso (¿se siguieron los pasos obligatorios?) y sí persiste (validation-report.json), alimentado automaticamente desde eventos reales de Devin (SessionStart/PostToolUse/SessionEnd) via el adaptador. Se puede pasar uno y fallar el otro.

Ejemplos de uso 
# Ejemplos
./bin/matrix hooks pre_activation_check '{"project":"mck"}'
./bin/matrix hooks validate_phase_close '{"phase":"develop","e2e":true,"evidence":"ran pytest, 12/12 pass"}'
./bin/matrix hooks validate_phase_close '{"phase":"eval","e2e":true,"evidence":"...","lesson":"appended brain/data/lessons/mck.md"}'
./bin/matrix hooks post_run_audit '{"agent":"neo","steps":["load_config","resolve_context","pre_activation_check"]}'
./bin/matrix hooks the_source                    # regenerar
./bin/matrix hooks the_source '{"check":true}'   # validar sync

8. The Source — verdad generada

docs/SYSTEM_TRUTH.md se genera desde el brain vivo (agentes y hooks). Nunca se edita a mano. Reemplaza los 22 docs manuales del sistema anterior (que se desincronizaban). Un doc generado no puede driftear.

# Regenerar
./bin/matrix hooks the_source

# Verificar que esta en sync (exit 0 = ok, exit 1 = stale)
./bin/matrix hooks the_source '{"check":true}'

9. Optimizacion de costos (The Construct)

«Carga exactamente lo que necesitas, nada mas.» Codificado como reglas operativas y expuesto como capacidades abstractas.

  • code-nav — navegacion/edit a nivel de simbolo (Serena o equivalente) en vez de leer archivos enteros. 5-10x mas barato.
  • model_policy — cheap para trabajo mecanico, reasoning para problemas duros, auto para mixto. Declarado por agente; adapters/devin/adapter.yaml mapea cada tier a un modelo concreto y el Trainman lo escribe como frontmatter model: en cada skill/subagent generado. Hoy: cheap → swe-1-7-lightning (variante rapida, preview-priced hasta el 2026-08-08), reasoning → opus ($5/$25 por MTok, 1M contexto), auto → adaptive ($0.50/$2.00 por MTok, tasa intro; re-verificar al cerrar su ventana intro).
  • allowed-tools (least-privilege) — el adaptador Devin tambien resuelve las capabilities: de cada agente a un grant nativo allowed-tools: (categorias: read, edit, grep, glob, exec, mas mcp__server__tool), asi un especialista no puede ejercer herramientas que no declaro necesitar. Neo (skill, no subagent) queda sin restringir a proposito — ver DEVIN.md.
  • Delegacion — artefactos >10 KB van a un sub-agente con word cap, para no inflar el contexto.
  • Checkpoints de resume — escribir checkpoint antes de truncar contexto; split de sesion en cambios de modo (build → eval → fix).

El mapa completo esta en brain/data/capability-map.md.

10. Federacion (la flota)

Un subsistema es una nave: su propio master, su propio roster, su propio AGENTS.md, bajo brain/subsystems/<nave>/. Las naves coordinan solo a traves del ledger Link compartido — nunca tocando el estado de otra.

NaveFuncionCapitan
NebuchadnezzarLa nave core (este sistema)Neo
LogosResearch profundo con evidencia graduada (GRADE), corpus estructurado, gate de integridadNiobe

Agregar una nueva nave:

  1. Crear brain/subsystems/<nave>/AGENTS.md con el contrato de la nave.
  2. Crear los agentes de la nave bajo brain/subsystems/<nave>/agents/.
  3. Coordinar con el core solo via el ledger Link (research:request / research:result, etc.).

11. AFK / The Hardline (opt-in)

Modulo desacoplado para eventos externos. Con Telegram la ruta real es: mensaje de Telegram → telegram-bridge.py → modules/hardline/inbox.log → hardline-monitor.sh → bin/matrix hardline dispatch → queue, single-flight, adapter, ack y trail Link. El monitor bloquea en tail -F: cero tokens mientras espera. El bridge usa solo long polling saliente de getUpdates; no abre puertos ni usa webhook.

# Proceso 1: iniciar el monitor (foreground; correr bajo tmux o process manager para AFK)
modules/hardline/hardline-monitor.sh

# Proceso 2: iniciar el bridge de Telegram, con el token ya provisionado en su entorno
modules/hardline/telegram-bridge.py

# Formato del mensaje de Telegram, una sola línea:
# <proyecto> <tarea>
# Ejemplo: mck Actualizar el README con una nota de una línea sobre Hardline
# El bridge escribe: mck|Actualizar el README con una nota de una línea sobre Hardline

Setup del bridge de Telegram

  1. En Telegram, abrir @BotFather, enviar /newbot, completar los prompts y copiar el token. Es una contraseña: nunca va como argumento CLI ni en código, inbox.log, queue, checkpoints o Link.
  2. Proveer el token exclusivamente al entorno del proceso bridge: export MATRIX_HARDLINE_TELEGRAM_BOT_TOKEN='pegar-token-aqui'. Para un servicio AFK, usar keychain/secret store del SO o un environment file con permisos restringidos que lea el servicio. Para rotarlo, reemplazar ese secreto externo y reiniciar el bridge; no se cambia código.
  3. Se recomienda restringir el bot al chat personal. Mandar primero un mensaje cualquiera al bot y, con el token en el entorno, ejecutar modules/hardline/telegram-bridge.py --show-chat-ids. Imprime los chat IDs numéricos pendientes sin escribir el inbox y guarda el cursor, por lo que esos updates mostrados no se despachan después. Elegir el propio y exportar MATRIX_HARDLINE_TELEGRAM_ALLOWED_CHAT_ID='tu-chat-id-numerico'. Esta variable es opcional para permitir un bot multi-chat deliberado; si está definida, cualquier otro chat se ignora. Alternativamente se puede consultar el ID con un bot de lookup como @userinfobot, pero el comando del bridge lo verifica contra los updates reales del bot.
  4. Ejecutar monitor y bridge como dos procesos persistentes separados, por ejemplo en dos panes de tmux, como arriba.
  5. Mandar al bot exactamente <proyecto> <tarea> en una sola línea. El proyecto debe estar registrado y bound; debe usar solo letras, números, punto, guion bajo o guion. El bridge divide en el primer espacio y convierte a <proyecto>|<tarea>. Mensajes multilinea, no textuales, sin tarea o con proyecto inválido se ignoran.

El cursor no secreto para reanudar long polling queda en brain/state/hardline/telegram-offset; se actualiza incluso para updates ignorados y evita replay luego de un reinicio. Borrarlo solo si se quiere reconsiderar updates aún pendientes. getUpdates no funciona mientras el bot tenga un webhook activo: este deployment usa long polling y no webhook.

Para probar solo el parser sin token: modules/hardline/telegram-bridge.py --parse-response PATH lee un JSON guardado de getUpdates, imprime las líneas aceptadas proyecto|tarea y no hace red ni escribe el inbox.

Seguridad: el token solo se lee de MATRIX_HARDLINE_TELEGRAM_BOT_TOKEN dentro del bridge; no se acepta como argumento, no se loguea ni se escribe. No mandar secretos como tarea: el monitor rechaza líneas que parecen secretos, pero no es un canal seguro de entrega de secretos. El gate existente de dispatch impide commit/push.

12. Modo autonomo (Commander Lock)

Cuando un flujo de trabajo corre en modo --headless (sin operador), Commander Lock actua como guardrail:

  • Valida el formato del prompt autonomo. Si no matchea, TASK_ABORTED.
  • Reglas FS absolutas: no tocar archivos fundacionales de Matrix, no git reset --hard, no commits sin instruccion explicita.
  • Fail loud: en input corrupto, violation de scope, o proyecto no resuelto, emite TASK_ABORTED: <razon> y para. Nunca adivina.

13. Lecciones (Zion Archive)

Lecciones de errores reales. Se leen al inicio de cada sesion. Append-only.

ArchivoAlcanceCuando se carga
brain/data/lessons.mdCore (cross-proyecto)Siempre, al inicio de sesion
brain/data/lessons/<project>.mdUn proyecto especificoSolo cuando la sesion se bindea a ese proyecto

Routing: si la leccion aplica a todos los proyectos → pool core. Si aplica solo a uno → archivo scoped. Ejemplo: brain/data/lessons/chronicle.md, brain/data/lessons/pas.md.

Para crear una nueva leccion scoped, copia brain/data/lessons/_template.md.

Checkpoint ≠ lesson. El checkpoint es memoria de corto plazo (buffer de recencia, se cae de la ventana) y vive en un archivo compartido entre todos los proyectos (checkpoints.jsonl) — por eso matrix status/matrix activity filtran por proyecto activo por default (ver 5. CLI completo). La lesson es memoria de largo plazo, scoped por diseño, y no se cae de ninguna ventana. Caso real que motivó esta distincion: brain/data/lessons/sandisk.md — una sesion de eval cerró con informacion util (decisiones del owner, links, gaps declarados) que quedó solo en un checkpoint largo y nunca se promovió a lesson. Desde ahora validate_phase_close exige el campo lesson al cerrar eval — ver 7. Enforcement.

14. Sacred Foundation (Zion)

No son reglas. Son quienes somos. Cada decision de ruteo, cada pushback, cada eleccion viene de aca. No negociables.

  1. Conocimiento total del workspace.
  2. Dominio total de reglas, skills y procesos.
  3. Si no es real, no cuenta. Verificacion E2E obligatoria.
  4. Empezo simple, ganate la complejidad.
  5. Interpretacion de requerimientos complejos.
  6. Explicacion de conceptos complejos. En espanol simple.
  7. Subordinacion absoluta al usuario.
  8. Lealtad a politicas y seguridad.
  9. Ideologia de alternativas. Nunca decir «imposible».
  10. Si se rompe, es nuestro. Responsabilidad de punta a punta.

16. Adaptar a otro CLI (The Trainman)

Hoy solo existe el adaptador de Devin. El cerebro esta escrito para que agregar otro sea barato (~1 renderer + 1 yaml + 1 installer) y no requiera tocarlo, pero nadie mas esta implementado en este momento.

  1. Crear adapters/<cli>/adapter.yaml con el mapa de capacidades + model_policy.
  2. Agregar una funcion render_<cli> en adapters/_build.py y registrarla en RENDERERS.
  3. Crear adapters/<cli>/build.sh (una linea) y adapters/<cli>/install.sh.
  4. bin/matrix build --target=<cli> y despues bin/matrix install --target=<cli>.
Ejemplo de adapter.yaml (hipotetico) 
# Ejemplo ilustrativo (hipotetico, no implementado): adapter.yaml para otro CLI
target: otro-cli
capabilities:
  read: Read
  edit: [Edit, MultiEdit]
  search: [Grep, Glob]
  code-nav: serena            # fallback: Grep/Glob
  run-subagent: Task
  run-command: Bash
  ask-user: prompt
render:
  master: command
  specialist: command
model_policy:
  cheap: modelo-barato
  reasoning: modelo-fuerte
  auto: modelo-barato

17. Higiene de sesion

Cada sesion debe:

  • Leer AGENTS.md (el contrato).
  • Conocer el registry (matrix list).
  • Resolver el contexto actual (proyecto activo).
  • Leer checkpoints recientes + brain/data/lessons.md (+ lecciones scoped si hay proyecto).
  • Respetar los boundaries de cada agente.
  • Nunca loguear secretos.
  • Escribir checkpoint cuando algo importa.
  • Verificar realidad antes de declarar «listo».

18. Lo prohibido

  • Dejar que el usuario hable directo con especialistas (sin pasar por Neo).
  • Mostrar menus o listar especialistas sin que lo pidan.
  • Loguear datos personales o sensibles.
  • Commitear secretos o keys.
  • Violar la sacred foundation.
  • Cruzar domain boundaries (cada agente hace lo suyo).
  • Mutar archivos de estado a mano (usar bin/matrix).
  • Declarar «listo» sin un check E2E.
  • Invocar git autonomamente (solo con pedido explicito del usuario).

Mi checkpoint reciente no aparece en matrix status/matrix activity

Desde esta version, ambos comandos filtran por default al proyecto resuelto (symlink _brain del directorio donde estas parado > primary de .context.yaml). Si tu checkpoint es de otro proyecto, no vas a verlo salvo que pidas la vista global: matrix status --all o matrix activity --project=<nombre>. Antes de este fix, la vista era global y sin filtrar — un checkpoint de otro proyecto podía «tapar» el tuyo en sesiones cross-project.

Cual es la diferencia entre validate_phase_close y post_run_audit?

validate_phase_close pregunta si el trabajo es real (evidencia E2E, y desde ahora una lesson capturada al cerrar eval); no escribe nada en disco, es una llamada manual del agente. post_run_audit pregunta si se siguió el proceso obligatorio de activación; sí persiste (validation-report.json) y se alimenta solo, desde eventos reales de Devin via el adaptador.
