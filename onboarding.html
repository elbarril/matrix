Canal 1 / 12 (tour)

Qué es Matrix

Matrix es tu capa de inteligencia personal: un repositorio raíz con el cerebro, conectado a cada proyecto por un symlink _brain. Se organiza en tres capas (adaptador, cerebro agnóstico, orquestación) y nunca copia inteligencia al proyecto.

  1. Usuario"¿qué es Matrix?"
  2. Neorutea internamente sin mostrar menú de especialistas y responde en español simple (Foundation 6).
  3. HarnessDevin CLI ejecuta la respuesta de Neo con las herramientas que el adaptador le mapeó — Neo nunca nombra al CLI.
Paso 1/3 del ejemplo
Ficha técnica: las tres capas 
LAYER 3 — Adapters · "The Trainman"
  adapters/devin/   (adapters/<otro>/ mas adelante, ninguno mas existe hoy)
  Transito entre mundos. Mapea capacidades a herramientas nativas.
  Genera artefactos: bin/matrix build --target=devin
  Los despliega globalmente: bin/matrix install --target=devin

LAYER 2 — Intelligence core · "Zion" (agnostic markdown)
  brain/agents/      → Neo (master) + especialistas
  brain/data/        → lessons, capability-map, code-quality lens
  AGENTS.md          → el contrato canonico
  NUNCA nombra un CLI. Habla en capacidades.

LAYER 1 — Orquestacion & infraestructura
  bin/matrix   → registry, proyectos, checkpoints, ledger (Link)
  hooks/       → enforcement portable (Seraph)
  brain/state/ → estado file-based
  No sabe nada de agentes. Gestiona estado y dispara hooks.

Regla de oro: la Capa 2 nunca nombra un CLI. Si algo solo funciona bajo un CLI, pertenece a un adaptador (Capa 3), no al cerebro.

La tesis central: agentes, lecciones y contrato se escriben una sola vez en markdown, hablando de capacidades abstractas (read, edit, search, code-nav…), nunca de un CLI puntual. Un adaptador fino («The Trainman») traduce esas capacidades a las herramientas nativas del CLI en uso.

El roster (agentes)

Un master (Neo) y cinco especialistas core, más uno opt-in (Commander Lock). Disciplina de roster: agregar uno requiere retirar o fusionar otro.

  1. Usuario"quiero refactorizar el onboarding" (ambiguo: ¿planear, diseñar o construir?)
  2. Neorutea a Morpheus para convertir la ambigüedad en scope ordenado.
  3. Neopasa el plan al Architect (cómo encaja) y después a Trinity (implementa).
  4. HarnessAgent Smith corre el gate E2E antes de que Neo diga "listo".

Quick Start

El flujo end-to-end completo: registrar un proyecto, bindearlo, verificar, y empezar a invocar a Neo.

  1. Usuario./bin/matrix add mi-proyecto /ruta/al/proyecto y ./bin/matrix select mi-proyecto.
  2. HarnessCapa 1 crea el symlink _brain dentro de mi-proyecto/ apuntando a este repo.
  3. Usuarioabre Devin CLI en mi-proyecto/ e invoca /neo.
  4. Neodetecta el symlink, carga el contrato y checkpoints recientes, y saluda listo para trabajar.
Paso 1/4 del ejemplo
Ficha técnica: los comandos completos 
# 1. Registrar un proyecto
./bin/matrix add mi-proyecto /ruta/al/proyecto

# 2. Seleccionarlo (crea el symlink _brain)
./bin/matrix select mi-proyecto

# 3. Verificar
./bin/matrix status

# 4. (Opcional) Calentar multiples proyectos
./bin/matrix work mi-proyecto
./bin/matrix work otro-proyecto

# 5. Generar artefactos nativos y desplegarlos globalmente (Devin)

./bin/matrix install --target=devin

# 6. Invocar a Neo desde Devin CLI, en cualquier proyecto
#    /neo

# 7. Escribir un checkpoint cuando algo importa
./bin/matrix checkpoint "Completado el fix del login"

# 8. Ver el ledger de actividad
./bin/matrix activity 10
Canal 6 / 12 (tour)

Enforcement (Seraph)

Hooks portables en hooks/, Python con contrato JSON in/out. Se corren vía bin/matrix hooks <nombre>. Son 16 hooks en total (ver ficha técnica).

  1. Usuariopide cerrar una fase de trabajo.
  2. Neollama matrix hooks validate_phase_close '{"phase":"develop","e2e":true,"evidence":"..."}'.
  3. Harnessel hook responde PASS o BLOCK; Neo reporta el veredicto sin inventarlo.
Paso 1/3 del ejemplo
Tabla de hooks (16 hooks)
HookQue haceCuando
pre_activation_check Valida: contrato presente, config valida, roster intacto, estado OK Antes de que cualquier agente actue
validate_phase_close Bloquea cerrar una fase sin evidencia real E2E. Implementa Foundation 3. En phase=eval tambien exige un campo lesson no trivial (que se capturo y donde, o un N/A razonado) — no escribe nada en disco, solo devuelve PASS/BLOCK Antes de declarar una fase «done»

the_source Genera docs/SYSTEM_TRUTH.md desde el brain vivo. Con {"check":true} valida que no hay drift. Mantenimiento / verificacion
audit_event Log append-only de metadatos de eventos de ciclo de vida (metadata-only, nunca contenido de prompts) Cada evento de lifecycle
session_close Cierre manual/CI de sesion: reconstruye los pasos desde el audit log y corre post_run_audit para generar el reporte de validacion Al cerrar una sesion

install_integrity_check Verifica que la instalación global (skills/agents desplegados) coincide con lo generado por build Después de install
pre_exec_guard Guarda previa a ejecutar comandos potencialmente destructivos Antes de correr comandos
validate_layer2 Valida que la Capa 2 (agentes, contrato) mantiene su forma canónica Mantenimiento
validate_lessons Valida el formato de brain/data/lessons.md y lecciones scoped Mantenimiento
surface_budget Presupuesto de tamaño (warn/fail) para la superficie documental compartida: AGENTS.md, DEVIN.md, brain/agents/neo.md. WARN-only, nunca bloquea; ok:false solo si excede fail Boot WARN / mantenimiento
validate_routing_signal Valida que las señales de ruteo entre agentes tengan la forma esperada Mantenimiento

Dos gates, dos preguntas distintas: validate_phase_close audita el contenido (¿el trabajo es real?) y no persiste nada — es el agente quien decide invocarlo al cerrar una fase. post_run_audit audita el proceso (¿se siguieron los pasos obligatorios?) y sí persiste (validation-report.json), alimentado automaticamente desde eventos reales de Devin (SessionStart/PostToolUse/SessionEnd) via el adaptador. Se puede pasar uno y fallar el otro.

./bin/matrix hooks the_source '{"check":true}'   # validar sync
Canal 7 / 12 (tour)

The Source — verdad generada

docs/SYSTEM_TRUTH.md se genera desde el brain vivo (agentes y hooks). Nunca se edita a mano. Un doc generado no puede driftear — pero solo si se regenera después de cada cambio.

  1. Devagrega un hook nuevo en hooks/ pero no regenera el doc.
  2. Neocorre matrix hooks the_source '{"check":true}' antes de declarar algo "listo".
  3. Harnessel hook compara el brain vivo contra SYSTEM_TRUTH.md y devuelve in_sync:false si hay drift.
  4. Neocorre matrix hooks the_source (sin check) para regenerar y cerrar el drift.
Paso 1/4 del ejemplo
Ficha técnica: comandos + drift conocido 
# Regenerar
./bin/matrix hooks the_source

# Verificar que esta en sync (exit 0 = ok, exit 1 = stale)
./bin/matrix hooks the_source '{"check":true}'

Drift histórico, resuelto (D5, esta sesión regeneró docs/SYSTEM_TRUTH.md): antes de D5, docs/SYSTEM_TRUTH.md listaba menos hooks que el árbol vivo (hooks/*.py, excluyendo _common.py); hoy ambos coinciden en 16 (bin/matrix hooks the_source '{"check":true}' reporta in_sync:true). Este onboarding usa 16 en todo su cuerpo.

Canal 9 / 12 (tour)

Federación (la flota)

Un subsistema es una nave: su propio master, su propio roster, su propio AGENTS.md. Las naves coordinan solo a través del ledger Link compartido — nunca tocando el estado de otra.

  1. Usuariopide research profundo, con muchas fuentes en conflicto.
  2. Neoescribe research:request en el ledger Link para la nave Logos.
  3. Sparksingiere fuentes vía matrix corpus-ingest --topic=<t> --slug=<s>, siempre mediado por Niobe (Sparks no tiene run-command).
  4. Ghostgradúa cada fuente (high/moderate/low/very low, estilo GRADE) — nunca bloquea, solo gradúa.
  5. Niobecorre el gate final de integridad y escribe research:result en Link; Neo lo presenta al usuario.

Canal 10 / 12 (tour)

AFK / The Hardline (opt-in)

Módulo desacoplado que reacciona a eventos externos (Telegram) mientras estás lejos del teclado. Opt-in: el core funciona sin él, y el monitor cuesta cero tokens en idle.

  1. Usuariomanda un mensaje de Telegram: mck Actualizar el README.
  2. Harnesstelegram-bridge.py hace long-polling, valida el formato y escribe mck|Actualizar el README en modules/hardline/inbox.log.
  3. Harnesshardline-monitor.sh (bloqueado en tail -F, cero tokens en idle) despierta y llama matrix hardline dispatch.
  4. Harnessel dispatch encola el evento, hace single-flight por proyecto, y deja un trail en Link.
  5. Neoprocesa la tarea en el proyecto mck y el resultado queda consultable con matrix hardline status.

Control de procesos: modules/hardline/hardline-ctl.sh {start,stop,status,restart,webapp-start,webapp-stop,webapp-status}. Dashboard read-only opcional: modules/hardline/status-webapp.py en http://127.0.0.1:8765/, solo localhost.

Canal 11 / 12 (tour)

Modo autónomo (Commander Lock)

Cuando un flujo corre en modo --headless (sin operador), Commander Lock actúa como guardrail: valida el prompt, aplica reglas de filesystem duras, y falla ruidoso en vez de adivinar.

  1. Sistema headlessrecibe un prompt autónomo mal formado o ambiguo sobre el scope.
  2. Commander Lockdetecta que no matchea el formato esperado o viola una regla de FS.
  3. Harnessemite TASK_ABORTED: <razón> y para — nunca continúa adivinando.
Paso 1/3 del ejemplo
Ficha técnica: reglas del guardrail
  • Valida el formato del prompt autónomo. Si no matchea, TASK_ABORTED.
  • Reglas FS absolutas: no tocar archivos fundacionales de Matrix, no git reset --hard, no commits sin instrucción explícita.
  • Fail loud: ante input corrupto, violación de scope, o proyecto no resuelto, emite TASK_ABORTED: <razón> y para. Nunca adivina.

Es opt-in y de bajo costo (tier cheap del model policy); ver canal 8, Costos.

Canal 12 / 12 (tour)

Sacred Foundation (Zion)

No son reglas. Son quienes somos. Cada decisión de ruteo, cada pushback, cada elección viene de acá. No negociables.

  1. Agenteafirma "el bug es por un race condition en el checkpoint".
  2. Foundation 3exige distinguir explícitamente lo verificado (reproducido con evidencia real, ej. un log o un test que falla) de lo inferido (una hipótesis razonable sin confirmar todavía).

Lecciones (Zion Archive)

Lecciones de errores reales. Se leen al inicio de cada sesión. Append-only.

ArchivoAlcanceCuando se carga
brain/data/lessons.mdCore (cross-proyecto)Siempre, al inicio de sesión

Routing: si la lección aplica a todos los proyectos → pool core. Si aplica solo a uno → archivo scoped. Ejemplo: brain/data/lessons/chronicle.md, brain/data/lessons/pas.md. Para crear una nueva lección scoped, copiá brain/data/lessons/_template.md.

Checkpoint ≠ lesson. El checkpoint es memoria de corto plazo (buffer de recencia, se cae de la ventana) y vive en un archivo compartido entre todos los proyectos (checkpoints.jsonl) — por eso matrix status/matrix activity filtran por proyecto activo por default (ver canal 4, CLI). La lesson es memoria de largo plazo, scoped por diseño, y no se cae de ninguna ventana. Caso real que motivó esta distinción: brain/data/lessons/sandisk.md — una sesión de eval cerró con información útil (decisiones del owner, links, gaps declarados) que quedó solo en un checkpoint largo y nunca se promovió a lesson. Desde ahora validate_phase_close exige el campo lesson al cerrar eval — ver canal 6, Enforcement.

Adaptar a otro CLI (The Trainman)

Hoy solo existe el adaptador de Devin. El cerebro está escrito para que agregar otro sea barato (~1 renderer + 1 yaml + 1 installer) y no requiera tocarlo, pero nadie más está implementado en este momento.

  1. Crear adapters/<cli>/adapter.yaml con el mapa de capacidades + model_policy.
  2. Agregar una función render_<cli> en adapters/_build.py y registrarla en RENDERERS.
  3. Crear adapters/<cli>/build.sh (una línea) y adapters/<cli>/install.sh.
  4. bin/matrix build --target=<cli> y después bin/matrix install --target=<cli>.
Ejemplo de adapter.yaml (hipotético) 
# Ejemplo ilustrativo (hipotetico, no implementado): adapter.yaml para otro CLI
target: otro-cli
capabilities:
  read: Read
  edit: [Edit, MultiEdit]
  search: [Grep, Glob]
  code-nav: serena            # fallback: Grep/Glob
  run-subagent: Task
  run-command: Bash
  ask-user: prompt
render:
  master: command
  specialist: command
model_policy:
  cheap: modelo-barato
  reasoning: modelo-fuerte
  auto: modelo-barato

Higiene de sesión

Cada sesión debe:

  • Leer AGENTS.md (el contrato).
  • Conocer el registry (matrix list).
  • Resolver el contexto actual (proyecto activo, vía matrix scope).
  • Leer checkpoints recientes + brain/data/lessons.md (+ lecciones scoped si hay proyecto).
  • Respetar los boundaries de cada agente.
  • Nunca loguear secretos.
  • Escribir checkpoint cuando algo importa.
  • Verificar realidad antes de declarar «listo».
  • Cerrar con matrix session close cuando corresponda.

Lo prohibido

  • Dejar que el usuario hable directo con especialistas (sin pasar por Neo).
  • Mostrar menús o listar especialistas sin que lo pidan.
  • Loguear datos personales o sensibles.
  • Commitear secretos o keys.
  • Violar la sacred foundation.
  • Cruzar domain boundaries (cada agente hace lo suyo).
  • Mutar archivos de estado a mano (usar bin/matrix).
  • Declarar «listo» sin un check E2E.
  • Invocar git autónomamente (solo con pedido explícito del usuario).

./bin/matrix status        # ver el estado

El pre_activation_check falla

Corre ./bin/matrix hooks pre_activation_check y lee la lista de errores. Los mas comunes:

  • contract_present: falta AGENTS.md en la raiz de Matrix.
  • config_present: falta brain/config.yaml. Copialo de otro backup o crealo con user y language.
  • roster_intact: falta un agente en brain/agents/. Verificá que estén los 7+1.
SYSTEM_TRUTH.md está desactualizado (The Source stale) 
# Verificar
./bin/matrix hooks the_source '{"check":true}'
# Regenerar
./bin/matrix hooks the_source
Quiero agregar un nuevo CLI

Ver pestaña "Adaptar CLI" en este mismo canal. Costo: ~1 yaml + 1 función render + 1 installer. Ninguno está implementado hoy salvo Devin.

Quiero agregar un especialista nuevo

Roster discipline: agregar uno requiere retirar o fusionar uno existente. Crear el .md en brain/agents/ con el formato canónico (frontmatter + XML blocks). Luego regenerar The Source.

Quiero una nave federada nueva

Ver canal 9, Federación. Crear brain/subsystems/<nave>/AGENTS.md + agentes. Coordinar solo vía Link.

Dónde guardo lecciones de un proyecto específico?

En brain/data/lessons/<proyecto>.md. Copiar _template.md como punto de partida.

Mi checkpoint reciente no aparece en matrix status/matrix activity

Ambos comandos filtran por default al proyecto resuelto (foco de sesión con matrix focus > symlink _brain del directorio donde estás parado). Si tu checkpoint es de otro proyecto, no lo vas a ver salvo que pidas la vista global: matrix status --all o matrix activity --project=<nombre>.

Cuál es la diferencia entre validate_phase_close y post_run_audit?

validate_phase_close pregunta si el trabajo es real (evidencia E2E, y una lesson capturada al cerrar eval); no escribe nada en disco, es una llamada manual del agente. post_run_audit pregunta si se siguió el proceso obligatorio de activación; sí persiste (validation-report.json) y se alimenta solo, desde eventos reales de Devin vía el adaptador. Ver canal 6, Enforcement.
